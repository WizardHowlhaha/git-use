# 规则说明

这份文档解释 `skill/SKILL.md` 中每组规则的取舍，以及它与校验脚本的对应关系。规则本身以 `skill/SKILL.md` 为准，这里只补充背景。

## 为什么按内核风格写提交信息

Linux 内核的 patch 规范被大量下游项目沿用，原因是它同时满足三件事：

1. **可读**——`<subsystem>: <imperative summary>` 让 `git log --oneline` 在上百个提交里仍然可扫描。
2. **可传输**——一行标题、一段正文、一个 trailer 区块，是 `git format-patch`、`git am`、邮件网关都能稳定处理的格式。
3. **可校验**——行宽、空行、空白规则都可以用脚本判定，不依赖评审者的耐心。

所以本 skill 不发明新格式，而是把内核约束落到具体可执行的检查上。

## 为什么提交信息里不写测试结果

内核风格要求提交信息描述“改了什么、为什么”，而不是“跑了什么”。测试命令和结果属于**过程信息**，读者在评审时想知道的是改动是否正确，而不是作者的验证流水账。

因此：

- 提交信息中不出现 `Tested:`、`Validated with` 等段落；
- 必要的验证仍然必须执行，只是不写进提交信息；
- agent 在对话汇报里如实说明执行了哪些检查、结果如何、有什么风险。

这条规则容易被误读成“可以跳过验证”，所以在 SKILL.md 中同时写了“验证要求仍按 SKILL.md 执行”。

## 为什么保留提交签署

`Signed-off-by` 表示真实提交者的签署，位于正文末尾的连续 trailer 区块中，使用 `git commit -s` 生成。

启用 `--require-signoff` 时，脚本检查该 trailer 是否存在，并检查区块格式；签署身份是否真实仍由提交者负责。

## 为什么 AI 生成的测试默认不进提交

这条规则把“验证行为”和“提交行为”分开：AI 生成的测试用于本地验证是否存在问题，但仓库里的测试通常带有长期维护成本（命名风格、断言稳定性、与既有测试框架的兼容）。

因此默认不提交，除非用户明确要求。排除时按**片段**选择性暂存，而不是按文件名整体排除，以免误伤用户自己写的测试。

## 为什么 PR 正文要单独写，不复用提交信息

提交信息服务于 `git log`，PR 正文服务于**没参与讨论的评审者**。两者的读者、长度约束和结构都不同：

- 提交信息受 50/75 列限制，PR 正文不受；
- 提交信息不写验证结果，PR 正文在用户或模板要求时可以有独立的验证章节；
- 提交信息按提交切分，PR 正文按“最终改动”组织，多个提交合并进同一个 PR 时需要说明它们的前置关系。

## 校验脚本覆盖了什么

`skill/scripts/check_commit_message.py` 实现 SKILL.md 中可机器判定的部分：

| 检查项 | 对应规则 |
| --- | --- |
| frontmatter 缺失、缺少 name 或 description | skill 可被发现的前提 |
| subject ≤ 50 显示列、不以句号结尾、必须含 `<subsystem>: ` | 标题格式 |
| subject 后恰好一个空行 | 正文分隔 |
| 正文行 ≤ 75 显示列（按东亚字宽计算） | 行宽 |
| 无行尾空格、无制表符、无 CRLF、无连续空行 | 空白规则 |
| trailer 区块连续、位于正文后、每个 trailer 形如 `Key: value` | trailer 结构 |
| 使用 `--require-signoff` 时存在 `Signed-off-by` | 提交签署 |
| 消息以换行结尾 | 格式完整性 |

脚本**不**检查的部分：标题是否真正描述了改动、正文是否诚实、diff 是否正确、是否应该拆分提交。这些只能由评审者或 agent 判断，脚本刻意不去猜。

## 与目标仓库规则的关系

仓库自身的贡献规则、维护者要求和 CI 规则**优先于**本 skill 的通用约束。例如某个仓库要求 `feat(scope): ...` 形式的主体、使用自己的 DCO 签核流程，或使用 Jira 编号，都以仓库规则为准；本 skill 的行宽、空白、trailer 格式等与具体项目无关的约束继续生效。
