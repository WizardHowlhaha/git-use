# PR 内容与排版规范

本规范提炼自一次内部 PR 评审中形成的“先说明问题与目标，再归纳行为变化，最后解释提交依赖”的写法。
参考材料中的产品、数字、开关默认值及 SHA 只属于该历史改动，不作为其他 PR 的事实；
本文件不保留任何内部系统地址或具体 PR 编号。

## 标题与语言

- 遵循目标仓库的标题习惯；未另行要求时，使用英文 `<type>: <summary>`，例如 `fix: archive build logs before downstream checks`。
- 标题概括最终改动的核心结果，不拼接多个 commit subject，不写笼统的“更新”或夸大效果。
- 正文默认中文，文件路径、函数名、参数、状态值及提交 SHA 保留原文并使用行内代码。
- PR 标题不强制套用 commit subject 的 50 列限制，正文也不按提交信息的 75 列硬换行；不自动附加 commit trailers。

## 内容结构

按以下顺序组织，篇幅随改动规模调整。单一小改动可以用短段落替代表格，
没有产物布局变化或提交依赖时省略对应章节，不为填模板添加空章节。

### 背景与目标

使用 `## 背景与目标`。先交代原有行为、具体问题及其影响，再说明本 PR 要达到的结果。
通常一至两段；必要时给出触发条件或前后示例。面向未读过聊天记录的评审者，
不写对话经过、调试流水账或已放弃方案，除非它们解释当前方案的重要取舍。

### 改动汇总

使用 `## 改动汇总`。先用一句话概括主要方向，少量加粗突出关键结果，
再按功能方向组织三列表格：

| 改动方向 | 原有问题 | 调整内容 |
| --- | --- | --- |
| 一个功能或行为方向 | 改动前的具体问题与影响 | 改动后的行为、适用条件及必要的默认值或兼容约束。 |

每行说明“为什么改、改成什么”，不逐文件罗列，也不直接抄 commit subject。
区分重构、可观测性、正确性修复与性能优化；前置重构不直接宣称为提速。

引用数量、耗时、并发度或收益时，注明数据来自何种配置、范围和观察方式，
并说明解释该指标所必需的限制。例如任务数量减少不能直接换算成耗时同比下降；
只读预演、代码推断和真实构建测量应明确区分。

### 按需补充的行为说明

当表格不足以解释关键行为时，增加具体主题的二级标题，例如
`## 日志归档布局与行为`、`## 配置与兼容行为`。

- 目录、产物或输出格式发生变化时，用 `text` 代码块展示简短布局，随后解释入口与可选文件。
- 参数或开关变化时写清名称、默认值、生效范围和开启／关闭时的行为。
- 失败处理、重试、回退或兼容性是本次改动的关键时，说明相应语义；不机械罗列所有未改变的行为。
- 默认在对话中汇报验证结果，不将验证过程写入 PR 提交条目。只有用户明确要求或仓库模板要求时才增加独立验证章节，简要记录实际结果与必要限制，不粘贴冗长命令输出。

### 各提交的主要改动与前置关系

多提交 PR 使用 `## 各提交的主要改动与前置关系`，按实际提交顺序列有序列表。
单条采用以下排版，说明段落随列表项缩进：

1. **`<short-sha>`：概括本提交的主要改动。**

   通常用一至两句说明问题根因和解决方案；确有前置关系时用一个短句补充。
   不重复前文的完整行为说明，不加入测试命令、验证结果、测试数量、日志回放过程或未执行验证的说明。

SHA 必须来自本 PR 实际提交范围；核对最终差异可使用 `git diff <base>...<head>`，
核对提交及顺序可使用 `git log --reverse <base>..<head>`。先解析实际仓库与引用，
不要猜测 base/head，也不要混入已在目标分支中的提交。rebase、squash 或补提后重新核对。

## 更新已有 PR

更新是对最终改动说明的维护，不能退化为追加提交日志。先读取线上标题、正文和实际 base/head，保留用户的有效编辑，再将新增变更映射到相关章节：

| 位置 | 更新要求 |
| --- | --- |
| 标题 | 判断是否仍概括最终范围；新增内容改变主旨时调整。 |
| 背景与目标 | 将新增问题的触发条件、根因或目标融入原有叙述，不能只在结尾补一句“另有修复”。 |
| 改动汇总 | 同步调整概括句与对应表格行，说明原有问题和最终行为；独立方向增加一行。 |
| 行为说明 | 更新受影响的配置、失败处理、兼容性和边界，删除过时或矛盾表述。 |
| 提交清单 | 根据实际提交顺序和 SHA 更新，条目保持根因与方案的简述。 |

无关章节不机械重写。若只调整 PR 文字，不因此 amend/rebase 已推送的提交；用户明确要求修改 Git 提交信息时才另行处理。

发布前对照修改前后的 PR 正文检查：新增行为是否已出现在前面的对应章节，概括句与表格是否一致，提交条目是否简洁且无验证流水账。发布后重新读取并逐节核对，不能仅确认最后新增的提交条目存在。

## Markdown 排版

- 正文采用 `##` 二级标题；不另加一级标题重复 PR 标题。
- 标题、段落、列表、表格和代码块之间保留空行。列表的补充段落保持缩进，不变成脱离列表的新段落。
- 表格统一使用 `| 改动方向 | 原有问题 | 调整内容 |`；单元格不塞多段代码或完整日志，复杂行为放到独立说明段落。
- 加粗用于少量关键结果和提交条目标题；标识符用反引号，目录树使用 `text`，其他代码块标明语言。
- 保留真实换行，不把 `\n` 当作正文换行，不给整篇正文套代码围栏。发布前移除占位符和模板说明。

## 可复用正文骨架

下面是多模块、多提交改动的骨架；删除不适用部分并用实际事实替换占位内容。

````markdown
## 背景与目标

描述原有行为、具体问题及影响，说明本 PR 希望达到的结果。

## 改动汇总

本 PR 主要包括：**主要方向一、主要方向二**。

| 改动方向 | 原有问题 | 调整内容 |
| --- | --- | --- |
| 方向一 | 原有行为及问题 | 最终调整和必要的行为边界。 |
| 方向二 | 原有行为及问题 | 最终调整和必要的行为边界。 |

如有量化结论，在这里交代数据范围、来源及解释限制。

## 具体主题的布局与行为

说明入口、默认值和关键行为；仅在布局变化有助于理解时保留目录树。

```text
output/
├── index.html
└── logs/
```

## 各提交的主要改动与前置关系

1. **`<short-sha-1>`：第一项主要改动。**

   用一至两句说明根因与方案；确有依赖时简述前置关系。

2. **`<short-sha-2>`：第二项主要改动。**

   用一至两句说明根因与方案；仅在确有依赖时说明与前一项的关系。
````

## 发布与核对

优先使用 PR 工具提供的结构化标题和正文参数。使用 GitHub CLI 时，通过
`gh pr create --body-file <path>` 或 `gh pr edit --body-file <path>` 读取已写好的
Markdown 文件，避免在 Shell 命令字符串中内联多段正文。

发布后读取实际 PR，按前述更新要求逐节核对标题、正文、目标分支与提交范围；查看渲染结果，
尤其检查表格、代码围栏、列表缩进和真实换行。新增行为必须在正文对应章节中体现，正文应描述当前最终实现，
不要保留已经过时的参数、提交编号或先前讨论中的方案。
